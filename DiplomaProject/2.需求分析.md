# 2 需求分析

本章主要对“考研择校评估与考情查询小程序”进行需求分析。首先从经济、技术和市场三个维度进行系统的可行性分析；其次，紧扣解决“考研信息碎片化”的核心业务痛点，围绕数据对比、择校评估、RAG智能问答和备考打卡四大核心板块阐述系统的功能需求；接着，结合活动图对系统的核心业务流程进行梳理；最后，明确系统在性能、安全性等方面的非功能性需求。

## 2.1 可行性分析

### 2.1.1 经济可行性

本系统主要作为本科毕业设计及面向考研学生的决策辅助工具。开发阶段前端采用免费的微信开发者工具，后端采用开源免费的 Java 语言、Spring Boot 框架以及 MySQL 数据库。在系统部署阶段，可利用低成本的云服务器，并结合开源或低成本获取的考研考情数据集构建本地知识库。整体研发与运维成本极低，经济上完全可行。

### 2.1.2 技术可行性

本系统采用前后端分离架构，核心技术栈成熟且具备创新亮点。前端移动端采用微信小程序原生技术开发，保障跨平台的高响应体验；后台接口端采用 Spring Boot 与 MyBatis 框架。
**本系统的核心技术可行性亮点在于引入了 RAG（Retrieval-Augmented Generation，检索增强生成）技术**。在传统的 AI 调用基础上，系统首先将历年复试线、招生目录等结构化数据存入本地数据库，当用户提问时，系统先从本地检索出精准的考情数据，再将其作为上下文喂给大语言模型（如国内合规的大模型 API）进行生成。这一技术路线有效解决了通用大模型在考研垂直领域容易“幻觉”的问题，技术路径清晰可控，完全具备技术可行性。

### 2.1.3 市场可行性

近年来考研竞争日益激烈，考生在择校阶段面临最严重的痛点即为“信息高度碎片化”。各大高校的具体报录比、复试线、自命题大纲差异等硬核数据散落在各处。本系统摒弃了传统考研平台臃肿的“杂糅型”社区路线，精准聚焦于“信息服务 + 决策辅助”。依托微信庞大的用户基数，即开即用，直击考生数据对比与择校评估的刚需。因此，本系统在市场上具有极高的实用价值和市场可行性。

## 2.2 功能需求分析

为避免系统沦为杂糅的综合平台，本系统功能严格聚焦于四大核心模块：数据对比、择校评估、RAG问答、备考打卡。系统分为微信小程序用户端和 Web 后台管理端。

### 2.2.1 微信小程序用户端功能需求

（1）**考情查询与数据对比模块**
* **多维检索**：支持按地区、学科门类（如 0854 电子信息）、985/211 标签查询院校基础信息。
* **深度考情展示**：清晰展示目标院校专业的招生人数、历年总分复试线、单科线要求及专业课科目组合。
* **横向数据对比**：支持用户勾选 2-3 所目标院校（如中南大学与武汉理工大学的 22408 计算机考研数据），生成直观的考情对比表格或趋势图。

（2）**基于 RAG 的智能问答模块（技术亮点）**
* **考研政策与考情助手**：用户在交互对话框中输入择校疑问（如“武汉理工大学计算机专硕复试考什么”）。
* **检索与回答**：系统不依赖大模型自身模糊的记忆，而是基于 RAG 架构先检索本地院校库，再由大模型整理输出精准、无幻觉的答复。

（3）**择校评估测算模块**
* **个性化测算**：用户录入个人备考档案（本科背景、预估政治/英语/数学/专业课成绩）。
* **胜率评估**：系统将用户分数与目标院校历年录取最低分/平均分进行算法加权比对，输出客观的评估报告（如“冲刺”、“稳妥”、“保底”标签及雷达图分析）。

（4）**备考打卡模块**
* **进度管理**：提供轻量级的 To-Do List 目标拆解功能（如“完成数学基础轮”），结合日历视图进行每日复习打卡，形成闭环的备考辅助。

## 2.3 业务流程分析

（1）**择校评估业务流程**
流程描述：用户进入“择校评估”模块，首先填写或确认个人预估各科初试成绩；随后选择意向院校及专业；系统前端将数据提交至后端；后端计算模块提取该专业近三年的复试线与录取均分，与用户总分及单科线进行差值运算与权重评估；计算完成后，生成包含成功率标签及各科目优劣势雷达图的评估报告数据，返回前端渲染展示。

## 2.4 非功能性需求分析

除了满足核心决策辅助功能外，系统还需满足以下非功能性需求。

（1）**数据准确性与问答可靠性（RAG要求）**：考研择校容不得信息误差。系统在进行 AI 问答时，必须严格受限于本地检索出的事实数据，大模型的角色仅为信息归纳与解读，从技术层面杜绝“AI幻觉”，确保输出决策依据的 100% 准确性。
（2）**性能需求**：院校对比与考情检索属于高频操作，接口的平均响应时间应控制在 2 秒以内；同时，与外部大模型 API 的通信链路需增加超时处理机制，保障前端不卡顿。
（3）**安全性需求**：用户的预估分数与备考进度属于个人隐私，数据库传输需进行加密处理，严防数据泄露与恶意 SQL 注入。
（4）**界面交互需求**：针对信息展示的特点，前端界面在渲染长表格（如历年复试线对比）和图表（如评估雷达图）时，需确保在不同尺寸的手机屏幕上自适应且不发生错位，保证“信息去碎片化”的直观体验。

## 2.5 本章小结

本章充分吸纳了“信息服务+决策辅助”的设计理念，对系统需求进行了全面修正与深化。首先通过可行性分析论证了项目的实操性；其次，严格剔除杂糅功能，将需求精准锁定在“数据对比、择校评估、RAG智能问答、备考打卡”四大核心模块，并通过用例规约重点阐释了 RAG 问答的逻辑流转；最后，提出了对数据准确性极高要求的非功能性指标，为后续系统架构设计指明了清晰的方向。

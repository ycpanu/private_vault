### 1. 软件工程的基本概念与软件危机

**① 软件危机（Software Crisis）**

- **概念**：是指在计算机软件的开发和维护过程中所遇到的一系列严重问题。简单来说，就是落后的软件生产方式无法满足迅速增长的计算机软件需求。
    
- **产生原因**：
    
    1. 软件本身缺乏可见性，且规模和复杂度急剧增加。
        
    2. 开发人员缺乏正确的理论指导，认为“软件开发就是写代码”，忽视了前期的需求分析和后期的维护。
        
- **核心表现（踩分点）**：
    
    1. 经费预算经常超支，开发进度难以控制（经常延期）。
        
    2. 软件质量和可靠性差，经常出Bug。
        
    3. 软件文档不完整、不一致，导致**极难维护**。
        
    4. 开发出来的产品往往不能真正满足用户的需求。
        

**② 软件工程的基本概念**

- **定义**：将**系统化的、规范的、可度量的**方法应用于软件的开发、运行和维护的过程，即将工程化思想应用于软件。目的是为了克服“软件危机”，以较低的成本开发出高质量的软件。
    

---

### 2. 软件工程的三要素

这三者相辅相成，是现代软件工程的基石：

- **方法（Method）**：回答了“怎么做”的问题。它提供了建造软件在技术上的解决方法。（例如：面向对象分析方法、结构化设计方法）。
    
- **工具（Tool）**：回答了“用什么做”的问题。它为软件工程方法提供了自动或半自动的软件支撑环境。（例如：画UML图的 draw.io，写代码的 IDEA，做版本控制的 Git）。
    
- **过程（Process）**：回答了“何时做”的问题。它将方法和工具结合起来，规定了各个开发阶段的任务、步骤和产出物，确保项目有条不紊地进行。
    

---

### 3. 软件项目的开发路线及其作用（生命周期阶段）

这是软件从无到有的整个生命周期，每个阶段的作用如下：

1. **需求分析**：解决“系统必须做什么”。与用户沟通，提取真实需求，最终产出具有法律效力的《软件需求规格说明书》(SRS)。
    
2. **概要设计**：解决“系统整体怎么实现”。进行系统架构设计、数据库总体设计、划分子模块并定义模块间的接口。
    
3. **详细设计**：解决“每个模块具体怎么实现”。深入到每个模块内部，设计具体的算法逻辑、数据结构和类的详细属性。
    
4. **编程（编码）**：将详细设计的结果翻译成某种编程语言的代码，产出可执行的程序。
    
5. **测试**：目的是“发现并纠正错误”。通过单元测试、集成测试、系统测试等手段，确保软件质量符合需求。
    
6. **产品交付**：将测试通过的软件部署到用户的实际环境中，并进行培训和交接。
    
7. **维护**：软件上线后的长期工作。为了修复隐藏的Bug、适应软硬件环境变化或增加新功能而对软件进行修改。**（注意考点：维护阶段是整个软件生命周期中耗时最长、花费资金最多的阶段）**。

### 4. 软件开发的传统模型（极简速记版）

_因为课件上已经有了，这里帮你提炼成一句话记忆口诀：_

- **瀑布模型**：一步一步来，重文档，**怕改需求**。（适合需求极度明确的项目）
    
- **原型模型**：先做个草稿给客户看，**边看边改**。（适合需求极度模糊的项目）
    
- **螺旋模型**：瀑布+原型+**风险分析**，转圈圈。（适合大型、高风险、超贵的项目）
    
- **增量模型**：核心功能先上线，其他零件**慢慢加**。（适合需要快速抢占市场的大型项目）

### 3) 软件的架构

**▶ 概念（幻灯片未写，为你补充考试标准答法）：** 软件架构是系统的**高层结构**，它定义了系统由哪些关键组件（模块）构成，以及这些组件之间如何相互通信与协作。它不涉及具体的代码实现，而是系统的“设计蓝图”。

**▶ 原则：高内聚低耦合，SOLID** _(注：“高内聚低耦合”是软件设计的总方针，意思是模块内部的元素联系要紧密，模块与模块之间的依赖要尽量少。)_

以下是 **SOLID** 五大原则及幻灯片上的定义（重点背诵标粗部分）：

- **S - 单一职责原则 (Single Responsibility Principle)**
    
    - **定义**：一个类或模块**只有一个引起变化的原因**。
        
    - _(通俗理解：一个类只干一件事，不要又当爹又当妈。)_
        
- **O - 开闭原则 (Open/Closed Principle)**
    
    - **定义**：软件实体应**对扩展开放，对修改封闭**，通过抽象实现新功能而不改动已有代码。
        
    - _(通俗理解：加新功能时，只准加新代码，不准改老代码。)_
        
- **L - 里氏替换原则 (Liskov Substitution Principle)**
    
    - **定义**：**子类对象必须能替换父类对象**，且不影响程序准确性，确保继承的行为一致性。
        
    - _(通俗理解：凡是用到爸爸的地方，换成儿子去也必须能正常工作。)_
        
- **I - 接口隔离原则 (Interface Segregation Principle)**
    
    - **定义**：客户端**不应依赖其不需要的接口**，尽量使用**小而专**的接口。
        
    - _(通俗理解：不要给别人一大个包含了无用方法的“胖接口”，把它拆分成几个小接口。)_
        
- **D - 依赖倒置原则 (Dependency Inversion Principle)**
    
    - **定义**：**高层模块不应依赖底层模块**，抽象不应依赖细节。
        
    - _(通俗理解：大家都依赖接口/抽象类来办事，不要直接依赖具体的实现类。)_
        

**补充原则：**

- **分而治之原则**
    
    - **定义**：将复杂系统或大型任务逐步拆解为更小、更易管理的子问题或模块，分别处理后再整合，从而高效完成整体目标，降低耦合、提高内聚。

### 1. MVC 架构核心要点 (背诵版)

**▶ 核心思想：** 将**数据处理（Model）**、**界面展示（View）**、业务控制（Controller）分离，让代码结构更清晰、易维护。

**▶ 三大核心组件：**

- **Model（模型层）**
    
    - **核心职责**：负责数据管理与业务逻辑。它是系统最底层、最核心的部分，直接与数据库打交道。
        
- **View（视图层）**
    
    - **核心职责**：负责数据展示与用户交互界面。也就是用户最终看到的网页、App 界面。
        
- **Controller（控制层）**
    
    - **核心职责**：负责调度与中转，连接 Model 和 View。它接收用户的输入，调用对应的 Model 处理数据，再把结果交给合适的 View 去展示。
        

**▶ 主要优点 (高频考点)：**

1. 职责分离，代码结构清晰。
    
2. 高可维护性（改界面不需要动核心逻辑）。
    
3. 高可复用性（同一个 Model 可以同时给 Web 端和手机端提供数据）。
    
4. 便于**团队开发**（前端写 View，后端写 Model/Controller，互不干扰）。
    
5. 便于**测试**（可以单独测试核心业务逻辑）。

### 1. 分层模式 (Layered Pattern)

**▶ 核心思想：**

将复杂系统自上而下划分为多个层次，每层只向其**直接上层**提供服务，并调用其**直接下层**的服务，严格限制跨级调用。

**▶ 核心职责（以经典三层架构为例）：**

- **表现层 (UI Layer)**：负责接收用户输入和展示结果。
    
- **业务逻辑层 (BLL)**：负责系统的核心计算和业务规则处理。
    
- **数据访问层 (DAL)**：负责与底层数据库进行数据读写交互。
    

**▶ 主要优缺点：**

- **优点**：高内聚低耦合；结构极其清晰；修改某一层（如换个数据库）不影响其他层。
    
- **缺点**：有性能损耗（一个简单的请求也必须逐层穿透）；容易导致过度设计。
    
- **生活类比**：公司的汇报机制（员工 $\rightarrow$ 主管 $\rightarrow$ 经理），不能越级汇报。

### 2. 客户端/服务器模式 (C/S 架构)

**▶ 核心思想：**

将系统分为两个独立的端：前端提供图形界面的**客户端 (Client)**，和后端集中处理逻辑与数据的**服务器端 (Server)**。

**▶ 核心职责：**

- **客户端 (Client)**：负责提供用户交互界面、做简单的数据校验、向服务器发送网络请求。
    
- **服务器端 (Server)**：负责接收多客户端并发请求、执行核心业务逻辑、统一管理数据仓库、并返回响应。
    

**▶ 主要优缺点：**

- **优点**：数据安全性高（集中在服务器）；客户端可以随时随地分布式接入。
    
- **缺点**：服务器存在单点故障风险（服务器一挂，全盘瘫痪）；服务器容易成为性能瓶颈。
    
- **生活类比**：餐厅点餐（多桌顾客看菜单点菜 $\rightarrow$ 统一交由后厨做菜）。

### 3. 管道-过滤器模式 (Pipeline-Filter)

**▶ 核心思想：**

将数据处理过程分解为一系列独立的、顺序执行的加工组件，数据像流水一样穿过这些组件最终得出结果。

**▶ 核心职责：**

- **过滤器 (Filter)**：负责对流入的数据进行特定的加工、转换或清洗。
    
- **管道 (Pipe)**：数据传输的通道，负责将上一个过滤器的输出，原封不动地传给下一个过滤器的输入。
    

**▶ 主要优缺点：**

- **优点**：极高的可复用性，可以像搭积木一样随意拼接或替换过滤器；扩展新功能极方便。
    
- **缺点**：不适合交互性强的系统；数据来回打包/解包可能导致系统变慢。
    
- **生活类比**：工厂的流水线（零件组装 $\rightarrow$ 喷漆 $\rightarrow$ 质检 $\rightarrow$ 包装）。

### 4. 仓库模式 (数据中心模式 / Repository)

**▶ 核心思想：** 系统拥有一个中央数据存储区（仓库），周围环绕着多个独立的子系统。子系统之间互不通信，一切信息交换全靠读写中央仓库来完成。

**▶ 核心职责：**

- **中央仓库 (Repository)**：保存系统的核心状态和全部共享数据。
    
- **独立组件 (Components)**：围绕仓库运行，负责读取数据、执行特定任务并把结果写回仓库。
    

**▶ 主要优缺点：**

- **优点**：极其适合处理海量、复杂的共享数据；各组件之间极致解耦。
    
- **缺点**：中央仓库成了性能瓶颈；一旦更改核心数据结构，所有组件都得跟着改代码。
    
- **生活类比**：会议室的共享大白板（张三画图，李四看到后在旁边补充文字，两人互不说话只对白板操作）。

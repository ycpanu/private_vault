总体判断

这是一个结构清晰、模块划分合理、文档质量高的毕设/原型级项目（RK3566 边缘摔倒检测网关，C++17 + RKNN + OpenCV + MQTT + SQLite + spdlog）。但离"企业级"还差一大截，差距集中在自动化验证缺失、若干真实正确性 bug、工程治理三块。按优先级列如下。

P0 — 正确性 / 资源安全 bug（最该先修）

1. 悬垂线程 use-after-free：BuzzerController::triggerAlarm（src/hardware/BuzzerController.cpp:52-58）用 std::thread 捕获 this 后 .detach()，告警最多睡 3s。BuzzerController 是 main 栈对象，若关机前刚触发告警，detached 线程会在 main 返回后访问已析构对象。应像 VideoCacher 那样存储并 join。
2. 视频回放 FPS 失效：CameraStreamer::captureLoop 算了 delayMs（:103-111）但没用，循环固定睡 30ms（:142）。
3. 非标准 include 可能编译不过：CameraStreamer.hpp:8 写 #include <videoio.hpp>，应改为 <opencv2/videoio.hpp>（sysroot 只有这个路径）。当前 bin/ 里二进制是 8/20 的，最新树大概率编不过。
4. VLA（GCC 扩展）：RKNNInferencer.cpp:182 的 rknn_output outputs[numOutput_] 非标准 C++17，应改 std::vector。
5. 无界 writer 线程：VideoCacher::saveVideoAsync 每次告警 new thread 无上限，析构 join 可能卡死关机。
6. init 失败被静默吞掉：main.cpp:108-115 忽略 buzzer/db/mqtt 初始化失败，系统降级运行但不告警。rknn_query 返回值也被忽略（RKNNInferencer.cpp:89,101,110）。
7. 小泄漏：LocalDatabase 的 sqlite3_open 失败路径不 close handle。

P1 — 工程基础设施（几乎全缺）

- 测试：tests/ 空目录；无 gtest/catch2、无 CMake test 目标、无 enable_testing()。唯一"测试"是手动视频回放模式。
- CI/CD：完全缺失（无 GitHub Actions / GitLab CI / 任何 workflow）。
- 静态检查：无 .clang-format、.clang-tidy、.editorconfig、无 sanitizer（ASAN/UBSAN/TSAN）、无覆盖率。
- 可测试性架构：无接口/抽象层/DI，main.cpp 是 god object，模块只能靠两个 queue 解耦，难以单测。

P2 — 配置与代码卫生

- 配置默认值三处打架：buzzer pin（头文件 73 / ConfigManager 138 / config.json 138）、SQLite 路径（fall_detection_gateway.db vs fall_detection.db vs README）。
- 路径不一致：config 用硬编码 CWD 相对路径加载，log/视频用 exe 相对路径——换目录运行会静默回落到全默认。
- 魔法数字散落：pi 写死 3.14159265358979、letterbox 114、帧间隔 33/30ms、MQTT "FALL_DETECTED"/"CRITICAL" 字符串。
- 缩进不统一：ThreadSafeQueue.hpp 用 tab，其余用 4 空格。

P3 — Git 治理 / 部署运维

- ~79MB 模型二进制被跟踪（models/*.onnx/*.rknn），check*.onnx 是转换调试中间产物，应移 Git LFS 或外置存储。
- 误提交：apps/__pycache__/main.cpython-313.pyc、models/.claude/settings.local.json 在 git 里（.claude/ 只在根目录忽略）。
- 无 LICENSE（项目本身无 license，只有第三方 SDK 的）。
- 无部署产物：无 systemd service、Dockerfile、部署脚本、健康检查/监控。
- 文档：README 和答辩文档质量高，但缺 ADR、Doxygen/API 文档。

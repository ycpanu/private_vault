
## 1. 文档说明

本文档用于说明“基于 Linux 边缘网关的摔倒检测与预警系统”最终工程的主要技术栈、运行环境、系统分层及各技术组件的职责。

---

## 2. 项目总体技术架构

系统采用“边缘端智能分析 + 本地事件存储 + 网络告警推送 + Web 可视化管理”的总体架构。

```
USB 摄像头
    ↓
视频采集模块
    ↓
图像预处理模块
    ↓
RKNN 模型推理模块
    ↓
摔倒状态判断模块
    ↓
事件管理模块
    ├── SQLite 事件记录
    ├── 本地截图和短视频保存
    ├── MQTT 告警推送
    └── HTTP / WebSocket 数据服务
            ↓
        Web 管理端
```

系统主要划分为以下三个部分。

（1）边缘网关端：部署在香橙派 3B 上，负责摄像头采集、模型推理、摔倒判断、事件记录、告警发送及系统状态监控。

（2）模型训练端：部署在开发电脑上，负责数据集处理、模型训练、模型导出和 RKNN 模型转换。

（3）Web 管理端：用于查看设备运行状态、摔倒事件、告警结果、摄像头画面及系统配置。

## 4. 边缘网关端技术栈

### 4.1 开发语言

边缘网关端使用 **C++17** 作为主要开发语言。

主要原因如下。

（1）适合 Linux 原生应用开发。

（2）能够直接调用 OpenCV、RKNN Runtime、SQLite 和 MQTT 等原生库。

（3）具有较好的运行效率和资源控制能力。

（4）适合多线程、网络通信、设备访问和实时视频处理。

（5）便于构建长期运行的 systemd 后台服务。

### 4.2 构建系统

项目使用 **CMake** 统一管理编译和依赖。

主要职责包括：

（1）管理源文件、头文件和子模块。

（2）链接 OpenCV、SQLite、MQTT、spdlog 等第三方库。

（3）支持 Debug 和 Release 两种构建模式。

（4）统一生成 ARM64 平台可执行程序。

（5）支持单元测试和集成测试目标。

推荐构建方式：

```
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j4
```

### 4.3 视频采集与图像处理

使用 **OpenCV 4.x** 完成视频采集和图像处理。

主要功能包括：

（1）通过 V4L2 打开 USB UVC 摄像头。

（2）配置摄像头分辨率、帧率和图像格式。

（3）读取实时视频帧。

（4）完成图像缩放、颜色空间转换和裁剪。

（5）绘制检测框、状态文字和时间信息。

（6）保存摔倒事件截图及视频片段。

（7）为模型推理模块准备输入图像。

Linux 底层摄像头接口使用 **Video4Linux2（V4L2）**。OpenCV 作为上层封装，负责简化摄像头访问和图像处理。

### 4.4 AI 推理框架

边缘端采用 **RKNN Runtime** 调用 RK3566 的 NPU 完成模型推理。

主要技术组件如下。

|   |   |
|---|---|
|组件|用途|
|RKNN-Toolkit2|在电脑端将 ONNX 模型转换为 RKNN 模型|
|RKNN Runtime|在香橙派上加载并运行 RKNN 模型|
|RKNPU2 驱动|提供 RK3566 NPU 设备支持|
|OpenCV|完成模型输入预处理和推理结果可视化|

模型部署流程如下。

```
PyTorch 模型
    ↓
导出 ONNX
    ↓
RKNN-Toolkit2 转换和量化
    ↓
生成 .rknn 模型
    ↓
香橙派 RKNN Runtime 推理
```

边缘端不负责模型训练，只负责模型加载、推理和后处理。

### 4.5 摔倒检测算法

摔倒判定不只依赖单帧检测结果，而采用“人体检测 + 时序特征 + 状态机”的方式。

主要判断特征包括：

（1）人体检测框宽高比。

（2）人体中心点纵向变化。

（3）人体框高度和宽度变化。

（4）人体姿态或身体倾斜程度。

（5）连续帧检测结果。

（6）异常状态持续时间。

（7）模型置信度。

（8）告警冷却时间。

状态机设计如下。

```
NORMAL
  ↓
SUSPECTED_FALL
  ↓
FALL_CONFIRMED
  ↓
ALARM_SENT
  ↓
RECOVERED
```

各状态含义如下。

|   |   |
|---|---|
|状态|含义|
|NORMAL|人体处于正常活动状态|
|SUSPECTED_FALL|检测到疑似摔倒特征|
|FALL_CONFIRMED|疑似状态持续达到阈值，确认摔倒|
|ALARM_SENT|已生成事件并完成告警发送|
|RECOVERED|人体恢复正常状态或事件结束|

配置管理模块负责：

（6）支持部分配置的运行时更新。

### 4.7 日志系统

使用 **spdlog** 构建统一日志模块。

日志系统支持：

（1）控制台输出。

（2）日志文件输出。

（3）按文件大小或日期滚动。

（4）Debug、Info、Warning、Error 和 Critical 等日志级别。

（5）记录时间、线程号、模块名和日志内容。

（6）限制日志文件数量和保留周期。

建议日志分类如下。

|   |   |
|---|---|
|日志类型|内容|
|system.log|程序启动、停止和系统运行信息|
|camera.log|摄像头连接、采集和异常信息|
|inference.log|模型加载、推理耗时和推理错误|
|event.log|摔倒事件生成和处理记录|
|network.log|MQTT、HTTP 和 WebSocket 通信信息|
|error.log|系统异常和错误信息|

### 4.8 数据库

使用 **SQLite 3** 作为边缘端本地数据库。

选择 SQLite 的原因如下。

（1）无需单独部署数据库服务。

（2）资源占用较低。

（3）适合单设备本地事件存储。

（4）便于数据备份和迁移。

（5）C/C++ 原生接口成熟。

主要数据表包括：

|   |   |
|---|---|
|数据表|用途|
|device|保存设备基本信息|
|fall_event|保存摔倒事件|
|alarm_record|保存告警发送记录|
|system_status|保存设备运行状态|
|system_config|保存可持久化配置|
|media_record|保存截图和视频文件信息|

图片和视频保存在文件系统中，数据库只保存文件路径、时间、类型及相关元数据。

### 4.9 MQTT 告警通信

使用 **Eclipse Paho MQTT C/C++** 作为 MQTT 客户端库。

MQTT 主要用于：

（1）发送摔倒告警。

（2）发送设备在线状态。

（3）上报 CPU、内存、温度和推理帧率。

（4）接收远程控制指令。

（5）支持断线重连和离线消息缓存。

建议主题设计如下。

```
fall-gateway/{device_id}/alarm
fall-gateway/{device_id}/status
fall-gateway/{device_id}/heartbeat
fall-gateway/{device_id}/command
fall-gateway/{device_id}/response
```

告警消息使用 JSON 格式，例如：

```
{
  "event_id": "FD202607270001",
  "device_id": "opi3b-001",
  "event_type": "fall",
  "timestamp": "2026-07-27T14:30:00+08:00",
  "confidence": 0.93,
  "image_path": "/data/events/2026/07/27/FD202607270001.jpg",
  "alarm_status": "sent"
}
```

### 4.10 HTTP 服务

边缘端使用轻量级 C++ HTTP 库提供 RESTful API。

推荐使用以下方案之一：

（1）**cpp-httplib**：单头文件、依赖较少、适合嵌入式网关。

（2）Drogon：功能完整，但依赖和资源占用更高。

本项目优先采用 **cpp-httplib**。

主要接口包括：

```
GET    /api/v1/status
GET    /api/v1/events
GET    /api/v1/events/{id}
PUT    /api/v1/events/{id}/status
GET    /api/v1/config
PUT    /api/v1/config
GET    /api/v1/logs
GET    /api/v1/media/{id}
POST   /api/v1/system/restart
```

接口数据统一使用 JSON。

### 4.11 WebSocket 实时通信

使用 WebSocket 向 Web 管理端实时推送数据。

主要推送内容包括：

（1）设备在线状态。

（2）CPU、内存、磁盘和温度。

（3）模型推理帧率。

（4）摄像头工作状态。

（5）新增摔倒事件。

（6）告警发送结果。

（7）实时检测画面或压缩后的图像帧。

视频预览优先采用低帧率 JPEG 图像推送或 MJPEG 方案，避免直接在香橙派上部署复杂视频流媒体服务。

### 4.12 多线程与任务调度

使用 C++ 标准线程库实现多线程处理。

主要线程包括：

```
主控线程
摄像头采集线程
模型推理线程
事件处理线程
MQTT 通信线程
HTTP 服务线程
WebSocket 推送线程
系统监控线程
文件清理线程
```

线程间通信采用：

（1）线程安全队列。

（2）互斥锁 `std::mutex`。

（3）条件变量 `std::condition_variable`。

（4）原子变量 `std::atomic`。

（5）智能指针管理共享资源。

视频处理采用“最新帧优先”策略，避免推理速度不足时产生大量积压。

### 4.13 系统状态监控

系统监控模块通过 Linux `/proc`、`/sys` 和系统调用获取运行状态。

监控指标包括：

|   |   |
|---|---|
|指标|数据来源|
|CPU 使用率|`/proc/stat`|
|内存使用率|`/proc/meminfo`|
|磁盘使用率|`statvfs`|
|CPU 温度|`/sys/class/thermal`|
|系统运行时间|`/proc/uptime`|
|网络状态|`/sys/class/net`|
|摄像头状态|视频采集模块|
|模型状态|推理模块|
|MQTT 状态|MQTT 模块|
|推理帧率|推理模块统计|

### 4.14 本地文件存储

事件文件按照日期分类保存。

```
data/
├── database/
│   └── gateway.db
├── events/
│   └── 2026/
│       └── 07/
│           └── 27/
│               ├── images/
│               └── videos/
└── temp/
```

系统提供自动清理机制，可根据以下条件删除旧文件：

（1）超过保留天数。

（2）磁盘使用率超过阈值。

（3）事件已上传并完成处理。

## 5. 模型训练端技术栈

### 5.1 开发语言与环境

|   |   |
|---|---|
|技术|用途|
|Python 3.10|模型训练和转换脚本|
|PyTorch|深度学习模型训练|
|Ultralytics YOLO|人体检测或姿态检测|
|OpenCV-Python|数据处理和视频分析|
|NumPy|数值计算|
|ONNX|通用模型交换格式|
|RKNN-Toolkit2|ONNX 到 RKNN 的转换|
|Jupyter Notebook|实验和结果分析|

### 5.2 模型选择

最终模型需要满足以下条件：

（1）能够检测人体或人体关键点。

（2）模型体积小。

（3）适合 RK3566 NPU 部署。

（4）推理速度满足实时处理需求。

（5）量化后精度下降可接受。

可选方案如下。

|   |   |
|---|---|
|方案|特点|
|YOLOv8n / YOLO11n 人体检测|模型较小，部署相对简单|
|YOLO Pose 轻量模型|可利用人体关键点提高摔倒判断准确率|
|自定义轻量级摔倒分类模型|可对检测到的人体区域进行二次分类|

推荐采用“两阶段”方案：

```
人体检测或姿态检测
    ↓
提取人体框、关键点和时序特征
    ↓
边缘端状态机判断摔倒
```

### 5.3 模型转换流程

```
训练 PyTorch 模型
    ↓
导出 ONNX
    ↓
检查 ONNX 输入输出
    ↓
准备量化校准数据
    ↓
RKNN-Toolkit2 转换
    ↓
生成 RKNN 模型
    ↓
电脑端模拟测试
    ↓
香橙派 NPU 实机测试
```

转换时优先使用 INT8 量化，以提高 NPU 推理速度并降低内存占用。

## 9. 代码质量与开发规范

### 9.1 代码格式

使用 **clang-format** 统一 C++ 代码风格。

建议采用 Google 或 LLVM 风格，并在项目根目录保存：

```
.clang-format
```

### 9.2 静态检查

使用以下工具进行代码检查：

|   |   |
|---|---|
|工具|用途|
|clang-tidy|C++ 静态分析|
|cppcheck|检查常见错误和资源问题|
|compiler warnings|开启编译器警告|

推荐编译参数：

```
-Wall -Wextra -Wpedantic
```

### 9.3 错误处理

项目统一采用以下原则：

（1）可恢复错误通过返回值或异常上报。

（2）严重错误写入日志并安全退出。

（3）设备断开、网络断开等情况自动重连。

（4）禁止忽略数据库、文件和网络操作返回值。

（5）使用 RAII 管理文件、线程、数据库连接和模型资源。

## 13. 最终技术路线

项目最终采用以下技术路线：

```
Orange Pi 3B + Ubuntu 22.04
    ↓
C++17 + CMake
    ↓
OpenCV 摄像头采集和图像处理
    ↓
RKNN Runtime 调用 RK3566 NPU
    ↓
人体检测或姿态检测
    ↓
时序特征与状态机完成摔倒判断
    ↓
SQLite 保存事件
    ↓
MQTT 推送告警
    ↓
HTTP + WebSocket 提供数据服务
    ↓
Vue 3 管理端进行展示
    ↓
systemd 完成开机自启和异常恢复
```

该技术路线兼顾实时性、资源占用、可维护性、部署便利性和毕业设计完整性，能够覆盖 Linux 应用开发、C++ 工程化、计算机视觉、边缘 AI、网络通信、数据库和 Web 管理等核心内容。

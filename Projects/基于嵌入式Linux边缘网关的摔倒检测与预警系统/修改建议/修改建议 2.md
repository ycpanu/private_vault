### 一、 潜伏的 Bug 与内存/资源泄漏风险

**1. `VideoCacher` 的线程句柄泄漏（严重风险）** 在 `VideoCacher.cpp` 中，每次触发报警都会向 `writerThreads_` 容器 `emplace_back` 一个新线程去异步合成视频。

- **问题：** 这个容器只进不出，运行期间从未清理过已结束的线程对象。如果设备连续运行数月，触发了成百上千次报警，`writerThreads_` 会无限膨胀，最终导致内存泄漏或触及系统的线程上限。
    
- **企业级改造：** 不要频繁创建和销毁线程。应该改用**单消费者模式**：在 `VideoCacher` 内部维护一个带锁的 `std::queue<std::deque<cv::Mat>>`（任务队列）和一个**常驻的后台编码线程**。报警时只负责把快照推入队列，由常驻线程逐个消费和编码。
    

**2. `BuzzerController` 的竞态条件与野指针风险** `BuzzerController.cpp` 的 `triggerAlarm` 使用了 `std::thread(...).detach()` 来实现非阻塞报警。

- **问题 1（竞态条件）：** 如果 3 秒内连续触发两次报警，会产生两个游离的线程同时去写同一个 Sysfs 文件。线程 A 刚把电平拉低，线程 B 可能正在拉高，导致蜂鸣器状态错乱，甚至一直长鸣无法关闭。
    
- **问题 2（生命周期）：** 游离线程中隐式捕获了 `this` 指针（`[this, durationMs]`）。如果 `BuzzerController` 实例被析构（程序退出或模块重启），而 detach 的线程还在 `sleep_for`，醒来后访问 `gpioPin_` 或写文件时就会引发段错误（Segfault）。
    
- **企业级改造：** 取消 `detach`。采用一个单独的硬件控制线程和一个原子标志位 `std::atomic<bool> isAlarming` 或条件变量来管理蜂鸣器状态，确保同一时刻只有一个控制流在操作硬件。
    

**3. C++ 标准违规：VLA（变长数组）的使用** 在 `RKNNInferencer.cpp` 的推理函数中，使用了 `rknn_output outputs[numOutput_];`。

- **问题：** `numOutput_` 是运行期确定的变量，这种写法称为 VLA（变长数组），是 C99 的特性，**在 C++ 标准（包括 C++17）中是绝对禁止的**。它之所以能编译，仅仅是因为 GCC 默认开启了扩展支持。在企业中，开启严格编译选项（如 `-Werror -pedantic`）时，这行代码会直接导致编译失败。
    
- **企业级改造：** 改为使用 `std::vector<rknn_output> outputs(numOutput_);`。
    

### 二、 距离“企业级架构”的差距与完善方向

**1. 淘汰 Sysfs，拥抱 libgpiod** 项目中通过读写 `/sys/class/gpio` 来控制蜂鸣器。

- **差距：** Sysfs GPIO 接口在 Linux Kernel 4.8 之后已被官方标记为**废弃（Deprecated）**，并在较新的内核中被彻底移除。它的性能差且不支持多路复用的硬件中断。
    
- **完善：** 改用基于字符设备的 `libgpiod` 库来控制 GPIO。这能在面试中向面试官展现你对 Linux 内核演进的关注，而不仅仅是停留在网上的老教程。
    

**2. 数据库 I/O 阻塞主流程** `LocalDatabase::saveAlert` 包含同步的磁盘 I/O 操作。

- **差距：** 如果 SD 卡老化导致写入变慢，或者 SQLite 发生锁等待，调用 `saveAlert` 的那个线程会被卡住。如果在报警处理的主线程中直接调这个函数，会导致整个流水线拥堵，丢失后续的报警。
    
- **完善：** SQLite 的写操作应当放入独立的持久化队列（可以使用项目中现成的 `ThreadSafeQueue`），或者开启 SQLite 的 WAL（Write-Ahead Logging）模式以提升并发写入性能。
    

**3. 缺乏进程级保活机制（Watchdog）**

边缘网关通常部署在无人值守的恶劣环境中。目前代码虽然做到了线程不阻塞，但如果某个关键线程（如 AI 推理）死锁，整个程序就变成了“僵尸进程”。

- **完善：** 引入 Linux 的 `systemd` watchdog 机制，或者硬件看门狗（`/dev/watchdog`）。主循环每隔几秒“喂狗”一次，一旦死锁超时未喂狗，系统级强制重启网关，实现真正的 7×24 小时高可用。
    

**4. 队列等待机制的微小性能损耗** 在 `ThreadSafeQueue::push` 中，`cond_var_.notify_one();` 是在 `lock_guard` 的作用域内部调用的。

- **完善：** 这是一个经典的“悲观唤醒”问题。消费者被唤醒后，第一时间会去争抢锁，但此时生产者还没出作用域，锁还没释放，导致消费者白白进行一次上下文切换并再次阻塞。将 `notify_one()` 移到 `lock_guard` 作用域之外（可以通过局部代码块 `{}` 控制锁的粒度），能进一步压榨极限性能。

本章主要阐述“考研择校评估与考情查询小程序”的总体架构设计与技术方案。首先，设计系统的整体拓扑与逻辑架构，明确前端、后端与外部AI服务的交互机制；其次，对系统整体功能模块进行划分与演进设计；最后，深入开展数据库设计，包括概念结构设计（E-R图）和物理表结构的详细字段设计，为后续系统的详细设计与编码实现提供坚实的底层支撑。

  

## 3.1 系统架构设计

  

本系统采用前后端分离的开发模式，整体逻辑架构划分为展示层、业务逻辑层、数据持久层以及外部服务层。系统总体架构设计如图3-1所示。

  

图3-1 系统总体架构设计图

  

![](assets/3%20%20概要设计/file-20260518160427678.png)

  

（1）展示层（Client Layer）：面向普通考生的微信小程序端基于 UniApp + Vue3 构建，负责可视化图表（ECharts）的动态渲染、多校对比表单交互以及AI问答流式输出；面向管理员的后台管理端基于 Vue3 + Element Plus 构建，负责大规模考情数据的批量导入与清洗交互。

  

（2）业务逻辑层（Business Layer）：采用 Spring Boot 框架实现核心业务。包含院校检索服务、多维归一化对比服务、分位数评测算服务。同时，集成 RAG（检索增强生成）工作流组件，负责在用户发起 AI 咨询时，拦截请求、提取实体、检索本地库并将数据包装为可信 Prompt。

  

（3）数据持久层（Data Layer）：利用 MyBatis-Plus 简化单表数据访问，以 MySQL 8.0 作为关系型物理主库，存储核心招录指标与考生脱敏名单；引入 Redis 构筑高并发缓存屏障，承载报名季高频查询的学校字典与考情热点图表。

  

（4）外部服务层（External Service Layer）：系统通过安全机制动态调用第三方大语言模型 API，在其接收到经过本地事实数据约束的上下文（Context）后，生成不具“幻觉”的择校规划与复习策略建议。

  

## 3.2 系统功能模块设计

  

根据需求分析结果，系统从视图视角划分为“微信小程序用户端”和“Web后台管理端”两大子系统。系统功能模块结构如图3-2所示。

  

图3-2 系统功能模块结构图

  

![](assets/3%20%20概要设计/file-20260518160427682.png)

  

### 3.2.1 微信小程序用户端

  

（1）院校库查询模块：提供基于省份、院校层次（985/211/双一流）、专业代码的多条件复合检索，并支持院校主页的深度招录指标（分数线、考试科目、招生简章）详情展示。

  

（2）多维对比分析模块：支持将2-3所目标院校加入对比清单，由后端进行数据归一化处理后，以并列式表格和雷达图的形式直观呈现名额、分数线波动的横向差异。

  

（3）基于RAG的智能评测模块：包含“上岸概率测算”和“AI智能问答”两个子功能。用户输入模拟成绩后系统自动匹配历史录取分位数，并联动大模型生成防幻觉的垂直招录答疑。

  

### 3.2.2 Web后台管理端

  

（1）考情数据治理模块：集成 EasyExcel 组件，支持管理员批量导入、追加或覆盖更新《专业目录》、《一志愿统计》、《调剂来源》等庞大的招录 Excel/CSV 数据。

  

（2）系统维护模块：提供用户备考数据的安全审计、核心字典项维护、高频热点缓存的主动刷新等管理功能。

  

## 3.3 数据库设计

  

### 3.3.1 概念设计

  

根据考研择校系统的核心业务实体及其内在关联，设计了系统的全局概念模型（E-R图）。系统中核心实体包括：学校（dim_school）、院系（dim_department）、专业目录（major_catalog）、考研学生（user）、评测记录（evaluation_record）、一志愿考情统计（first_choice_stats）、调剂统计（adjustment_stats）、调剂来源流向（adjustment_source）、复试成绩统计（retest_score_stats）、复试名单（retest_list）、拟录取名单（admission_list）、管理员（admin）。各实体间的主要关系为：一所学校包含多个院系（1:N）；一个院系下设多个专业（1:N）；一名学生可创建多条评测记录（1:N）；每条评测记录关联一个目标学校及一个目标专业；每一条专业目录可对应一条一志愿考情统计、一条调剂统计和一条复试成绩统计（1:1）；一个专业可包含多条复试名单记录和拟录取名单记录（1:N）；调剂来源流向关联到学校与专业。系统全局E-R图如图3-3所示。

### 3.3.2 逻辑设计

  

将数据库概念设计模型细化为当前数据库管理系统所支持的逻辑数据模式。为消除原方案中的字段冗余和第一范式违规，本设计引入学校字典表（dim_school）和院系字典表（dim_department）作为维度表，其余事实表通过外键引用维度表获得学校及院系信息。数据表的概要描述如下所示。

  

（1）学校字典表（编号，院校代码，院校名称，所在地区，院校类别，创建时间，更新时间）。

  

（2）院系字典表（编号，所属学校编号，院系名称，创建时间，更新时间）。

  

（3）专业目录表（编号，年份，所属学校编号，所属院系编号，专业代码，专业名称，专业方向，学习形式，研究方向，招生人数，政治科目，外语科目，专业课一科目，专业课二科目，士兵专项计划，少干专项计划，备注，创建时间，更新时间）。

  

（4）用户信息表（编号，微信唯一标识，昵称，头像，初试政治预估成绩，初试外语预估成绩，初试数学预估成绩，初试专业课预估成绩，创建时间，更新时间）。

  

（5）后台管理员表（编号，登录账号，密码，角色，创建时间，更新时间）。

  

（6）评测记录表（编号，用户编号，目标学校编号，目标专业编号，评测时政治预估分，评测时外语预估分，评测时数学预估分，评测时专业课预估分，评测结果，创建时间）。

  

（7）一志愿考情统计表（编号，专业目录编号，报考人数，一志愿录取人数，调剂录取人数，最高分，最低分，平均分，备注，创建时间，更新时间）。

  

（8）调剂统计表（编号，专业目录编号，调剂录取人数，调剂最高分，调剂最低分，调剂平均分，备注，创建时间，更新时间）。

  

（9）调剂来源流向表（编号，学校编号，专业目录编号，考生编号，初试总分，一志愿报考院校，备注，创建时间，更新时间）。

  

（10）复试成绩统计表（编号，专业目录编号，复试人数，政治或管综平均分，外语平均分，专业课一平均分，专业课二平均分，最高分，最低分，备注，创建时间，更新时间）。

  

（11）复试名单表（编号，学校编号，专业目录编号，考生编号，考生姓名，政治或管综成绩，外语成绩，专业课一成绩，专业课二成绩，初试总分，专项计划，备注，创建时间，更新时间）。

  

（12）总拟录取名单表（编号，学校编号，专业目录编号，考生编号，考生姓名，初试总分，专项计划，备注，考生类别，创建时间，更新时间）。

|candidate_name|varchar|50||拟录取考生姓名（脱敏存储，生产环境建议哈希处理）|

|preliminary_score|decimal|6,2||该录取考生的初试最终总分|

|special_plan|varchar|50||该考生涉及的专项计划标签|

|remarks|text|0||拟录取状态的补充说明|

|candidate_type|varchar|50||考生类别属性（一志愿/调剂）|

|create_time|datetime|0||录取数据导入时间|

|update_time|datetime|0||录取数据最后校对的时间|

  

### 3.3.3 物理设计

  

**（1）数据库选型**

  

本系统选用 MySQL 8.0 作为关系型数据库管理系统，存储引擎采用 InnoDB，字符集使用 utf8mb4，排序规则为 utf8mb4_unicode_ci，以完整支持中文及特殊字符的存储与检索。同时引入 Redis 7.x 作为缓存中间件，缓存学校字典、专业目录等高频读取的低频变更数据，降低数据库读压力。

  

**（2）索引设计**

  

基于系统核心查询场景，为各表设计以下索引策略：

  

- dim_school：在 school_code 上建立唯一索引（UNIQUE INDEX idx_school_code），确保院校代码不重复；在 region 上建立普通索引（INDEX idx_region），支持按地区筛选。

- dim_department：在 school_id 上建立普通索引（INDEX idx_dept_school），加速按学校查询院系的 JOIN 操作。

- major_catalog：在 (year, school_id) 上建立复合索引（INDEX idx_year_school）；在 (school_id, dept_id) 上建立复合索引（INDEX idx_school_dept）；在 major_code 上建立普通索引（INDEX idx_major_code），支持按专业代码检索。

- user：在 openid 上建立唯一索引（UNIQUE INDEX idx_openid），保证微信用户唯一性并加速登录查找。

- admin：在 username 上建立唯一索引（UNIQUE INDEX idx_admin_username）。

- evaluation_record：在 (user_id, create_time) 上建立复合索引（INDEX idx_user_eval_time），支持按用户按时间倒序查询评测历史。

- first_choice_stats：在 major_catalog_id 上建立唯一索引（UNIQUE INDEX idx_fcs_major），因为每个专业每年只有一条一志愿统计记录。

- adjustment_stats：在 major_catalog_id 上建立唯一索引（UNIQUE INDEX idx_adj_major），同理每个专业每年只有一条调剂统计记录。

- adjustment_source：在 school_id 和 major_catalog_id 上分别建立普通索引（INDEX idx_as_school、INDEX idx_as_major），加速按学校或专业维度筛选调剂来源。

- retest_score_stats：在 major_catalog_id 上建立唯一索引（UNIQUE INDEX idx_rss_major）。

- retest_list：在 school_id 和 major_catalog_id 上分别建立普通索引（INDEX idx_rl_school、INDEX idx_rl_major），加速按学校或专业筛进复试名单。

- admission_list：在 school_id 和 major_catalog_id 上分别建立普通索引（INDEX idx_al_school、INDEX idx_al_major），加速按学校或专业筛拟录取名单。

  

**（3）视图设计**

  

为简化应用层查询并兼容原有扁平数据接口，建议按需创建以下查询视图：

  

- v_first_choice_detail：将 first_choice_stats 与 major_catalog、dim_school、dim_department 进行 JOIN，对外暴露包含学校名称、地区、专业方向等冗余字段的扁平视图，便于前端直接消费。

- v_adjustment_detail：同理，将 adjustment_stats 与维度表进行 JOIN，输出包含学校、专业全称的调剂统计视图。

- v_retest_detail：将 retest_score_stats 与维度表进行 JOIN，输出包含学校和专业完整信息的复试成绩统计视图。

  

视图的使用可让既有查询逻辑在规范化后以最小改动量平稳过渡。

  

**（4）配置参数建议**

  

- innodb_buffer_pool_size：设置为服务器物理内存的 60%~70%，以容纳热数据页。

- character_set_server：utf8mb4。

- max_connections：根据预估并发量设置为 200~500。

- slow_query_log：开启慢查询日志，long_query_time 设为 1 秒，便于后续性能调优。

- Redis 缓存过期策略：学校字典和热门专业目录采用 TTL 24 小时的惰性淘汰 + 主动刷新结合模式。

  

**（5）数据导入与 ETL 流程说明**

  

由于爬虫脚本产出的 7 份 Excel 数据为扁平结构（每行数据内嵌学校名称、地区、院校类别等字段），在导入规范化后的数据库之前需进行以下 ETL 步骤：

  

1. 提取学校维度：遍历所有 Excel 文件中的（学校代码/名称、地区、院校类别）组合，去重后导入 dim_school 表。

2. 提取院系维度：从专业目录 Excel 中提取（学校、院系名称）组合，通过学校名称关联 dim_school.id 后导入 dim_department 表。

3. 导入专业目录：将专业目录 Excel 中的行通过 dim_school.school_name 和 dim_department.dept_name 关联获得对应的 school_id 和 dept_id，写入 major_catalog 表，同时记录 Excel 行号与新生成 ID 的映射关系。

4. 导入事实表：其余 6 份统计/名单 Excel 数据通过相同关联方式获取 school_id 和 major_catalog_id 后写入对应事实表。

  

建议在 Spring Boot 项目中编写独立的 DataImportService，利用 EasyExcel 组件分批读取 Excel 并执行上述 ETL 流程，保证百万级数据行的高效入库。

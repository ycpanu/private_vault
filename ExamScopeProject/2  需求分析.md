本章主要对“考研择校评估与考情查询小程序”进行需求分析。首先通过经济、技术和市场三个维度进行可行性分析；其次，围绕院校信息库、考情数据对比分析、基于 RAG 的智能择校评测三大核心功能板块阐述系统的功能需求；接着，结合活动图对核心业务流程进行梳理；最后，明确系统在性能、安全性及数据准确性等方面的非功能性需求。

## 2.1 可行性分析

### 2.1.1 经济可行性
本系统主要作为本科毕业设计及面向考研学生的决策辅助工具。开发工具如UniApp、IntelliJ IDEA 以及后端框架 Spring Boot、数据库 MySQL 均为开源或免费版本。系统运行所需的云服务成本较低，且通过购买或采集获得的考研数据集具有较高的复用价值。整体研发与运维成本在个人可接受范围内，经济上完全可行。

### 2.1.2 技术可行性
系统采用前后端分离架构。前端利用UniApp框架，结合组件库实现高交互界面；后端采用 Java 语言配合 Spring Boot 框架，技术生态成熟。
**技术核心亮点在于 RAG（检索增强生成）技术的应用**。系统通过将本地考研考情数据库（MySQL）与大语言模型 API 相结合，通过检索增强的方式为模型提供垂直领域的背景知识，有效解决了通用 AI 的“幻觉”问题，确保择校建议的准确性。这一技术路线明确且已有成熟案例参考，技术上完全可行。

### 2.1.3 市场可行性
当前考研竞争日趋激烈，考生在择校时面临严重的信息碎片化痛点。相比于市面上功能臃肿、导流课程严重的综合性考研平台，本系统精准定位为“决策辅助工具”，去除了社交、打卡等无关干扰，直击考生对精准数据和科学评估的需求。这种垂直化的服务模式在当前考研市场中具有较强的差异化优势，市场可行性极高。

## 2.2 功能需求分析

本系统功能严格聚焦于数据查询与智能决策。系统分为微信小程序用户端和 Web 后台管理端。

### 2.2.1 微信小程序用户端功能需求
（1）**院校库与考情数据查询模块**
* **精准检索**：支持用户按院校名称、省份、985/211 标签及专业代码（如 0854 电子信息）进行筛选。
* **深度详情展示**：展示特定院校专业的历年招生人数、复试分数线（总分与单科）、专业课大纲及考试科目明细。

（2）**多维对比分析模块**
* **横向对比**：支持用户选择 2-3 所意向院校进行对比。
* **对比展示**：系统通过可视化表格或图表，直观呈现不同院校在录取难度、分数线波动、招生名额等维度上的差异，辅助用户做出初步筛选。

（3）**基于 RAG 的智能评测模块**
* **择校评估测算**：用户录入预估各科初试成绩（政治、英语、数学、专业课），系统根据目标院校往年录取分布给出“胜率评估”。
* **RAG 智能问答**：用户可就具体的报考疑问提问（如“中南大学 408 专硕复试权重是多少”），系统检索本地库后由 AI 生成精准回复。

## 2.3 业务流程分析

（1）**院校对比分析业务流程**
流程描述：用户在院校详情页选择“加入对比”；在对比清单中点击“开始对比”；前端发送选定的院校 ID 集合；后端查询各校对应年份的考情记录；系统对数据进行归一化处理后返回对比结果集；前端以并列式表格或雷达图展示数据差异。

## 2.4 非功能性需求分析

（1）**数据准确性**：作为决策辅助工具，系统展示的复试线、录取人数等数据必须经过人工或脚本的多重校验，AI 问答模块必须受到本地事实库的严格约束。
（2）**响应性能**：由于涉及外部 AI 接口调用及大量数据检索，院校库查询响应应在 1.5 秒内，AI 问答的首句生成响应不应超过 3 秒。
（3）**安全性**：需对用户的初试预估分数等私密备考数据进行加密存储，防止数据泄露。
（4）**易用性**：界面需针对复杂的对比表格进行移动端适配优化，确保在手机端浏览长报表时依然清晰直观。

## 2.5 本章小结
本章针对“聚焦信息服务与决策辅助”的核心目标，对系统需求进行了深度精简与重构，详细论证了各功能模块的设计初衷、业务逻辑及技术实现细节，并对数据的准确性提出了严格的非功能性指标要求，为后续的系统概要设计奠定了扎实基础。
